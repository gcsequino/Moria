# Closed indexing staging collection

This lifecycle path collects temporary `indexing_rows` spills after a real build closes. It preserves every published Source alias, key map and canonical population. An expired unpublished build can additionally discard its private key map, staged rows and never-activated projection relation. It does not delete identities, Object UID homes, Dataset roots, publication receipts or fence history.

`runtime_indexing_stage_closures` captures immutable actual terminal transitions: status, owner/fence, build-scope hash and server timestamp. Closed legacy/restored builds without such a record are observed under the real build lock at the current server time; their age starts at observation, never at an invented historical close time. A later retry/reclose has a distinct current closure identity.

`runtime_indexing_staging_once(policy)` uses an approved enabled history policy, the real operator and current control incarnation. Each transaction rechecks the latest actual closed status/owner/fence/scope and the policy's full age. Unpublished discard additionally requires an expired deadline and no published generation, alias, activated projection or live structural Search reference. Valid revision/read cursors resolve through published generations/aliases and therefore preserve their backing populations. An actual successor policy can continue same-scope committed work; an origin policy ID is not a permanent ownership capability.

Terminal transitions maintain a pending row for the latest closure. Separate partial indexes serve unknown closure times, known closure age and deferred retry time. Each call promotes at most eight due retries and makes two limited ready seeks before selecting at most eight candidates. Captured time parameters form actual index range conditions. Per-environment/current-incarnation legacy reconciliation advances a `(created_at,id)` cursor through at most eight closed builds per call; it skips completed latest work and never rescans the completed prefix. Future retries report their next time; current contention is distinct from future age. Current policies are environment-scoped, while selected build/store/target scope is still checked under its real locks.

Each cleanup step uses an exclusive per-build advisory TRY barrier followed by a build row lock with SKIP LOCKED. It never waits for task locks. Scan/reduce/coordinator/projection mutations take the shared barrier and check their current real claim after admission; retry uses the exclusive TRY barrier under its existing authority. Final publication rechecks the current claim after obtaining the build lock and cannot turn a cancelled/failed build back into ready. Generic non-build legacy staging retains its existing path.

Spill cleanup uses the existing `(build,partition,uid,task,fence)` index. Map and canonical cleanup use `(store,uid)` and `(stage,uid)`. Each page contains at most 1,000 keys and 16 MiB of actual PostgreSQL value storage, measured without returning wide payloads. Progress and actual deletion counters commit in that same transaction. Cursor exhaustion is cross-checked against remaining physical rows. Projection cleanup derives the relation from the actual owned projection record, requires no activation, takes backup-retention admission with TRY, and uses relation NOWAIT before dropping it. Header retirement follows actual empty closure.

The existing native `history-retention once` worker executes one bounded staging transaction, commits/releases its locks, then executes the existing published-history step in a separate bounded transaction. Both retain the existing five-second statement and 250-ms lock limits. The result preserves the history state and adds actual `indexingStaging` progress. When published history is complete or requires its next plan, actual pending staging remains visible as busy/progress; with no pending staging the original state is retained. It keeps draining eligible work/busy backpressure after the published lane completes, while future age/grace alone does not spin. Later ordinary calls reconsider newly eligible observed closures. These two independent transactions are not one atomic garbage-collection operation. Direct SQL `runtime_history_step` remains the published-history primitive.
