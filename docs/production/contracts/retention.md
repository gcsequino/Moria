# Retention and physical reclamation

Retention defaults to forever. An operator must approve a finite, immutable policy before any retirement or physical removal. A policy is scoped to the exact logical namespace revision, physical binding fingerprint, object class, and current instance incarnation. A producer write grant is not a removal capability.

Eligible implemented classes are exact issued recovery objects, privately journaled filesystem upload candidates, and qualified managed native Dataset roots and issued outputs under an explicit C04 policy. Each requires permanent producer retirement and current reference admission. Unknown objects discovered through a provider prefix are not candidates. External legacy Dataset roots remain ineligible; POSIX and unversioned physical deletion remain unsupported.

A removal claim binds the exact object and provider version, policy revision, owner, fence, lease, and incarnation. Before each provider use it checks current claim authority, producer tombstone, policy, and references. Candidate planning and final reference checks use the exclusive `moria/recovery-retention/v1` admission. Preparing, failed, and incomplete recovery sets retain original source members independently of ownership lease expiry. A ready set releases original source custody only after its immutable sealed manifest, metadata dump, complete content inventory, and independently stored exact-size/hash backup versions are durable. Those backup namespace copies and issued backup objects remain retained through the set retention policy. Retirement and physical deletion cannot infer abandonment from an expired lease alone.

Restoration may contain a sealed external manifest and verified inventory while its exported database snapshot lacks the subsequently written issued-object ledger. An empty restored ledger never proves orphanhood. Retain those backends and manifest closures conservatively until their exact membership has been rehydrated or independently verified under an explicit retirement policy.

S3 removal requires the qualified non-null VersionId primitive. ETag-only/null-version deletion is unsupported. The pinned MinIO server ignored a wrong DELETE If-Match header, so stat plus unqualified DELETE is excluded. POSIX removal remains unsupported until a private-quarantine/version comparison and recovery protocol is independently tested. A newer provider version or uncertain late completion remains a durable reconciliation obligation; a successful removal of one version does not prove that all late producer effects are impossible.

Whole-population JSON scans, prefix deletes, dropping stale rows, replacing actor credentials, or silently shortening Iceberg history are not valid substitutes. Policy/reference/fault tests and actual provider deletion tests are independent gates. This inventory describes required integration; it does not claim those gates are complete.

## Managed Dataset expiration controller

The native controller supports explicit finite policies for registered managed Dataset namespaces backed by qualified versioned S3 storage. Approval inventories every retained history root and rejects untracked legacy roots or an incompatible reader profile. The default remains retain forever; POSIX, external snapshots, and foreign-incarnation custody remain outside physical reclamation eligibility.

Actual native writer and maintenance capabilities journal object identity, physical binding, size and hash before provider effects. Sealed roots record exact immutable members and provider versions. Accepted executions pin their input and expected-head roots; indexing builds pin exact source roots. Active work remains pinned, and terminal executions retain roots for the result/receipt horizon. Materialized Object, Source and Search reads require their PostgreSQL generation history, rather than a physical Dataset replay pin merely because the read carries Dataset provenance.

Expiration constructs a metadata-only Iceberg rewrite that preserves the current snapshot, schema, retained snapshots and pinned roots. Exact qualified source versions authorize reuse without decoding unchanged data again. Its final transaction rechecks current policy, incarnation, head, lease and pins, then atomically publishes the new head and permanent expired-root markers. New pin/publication admission rejects an expired root. A concurrent admission barrier returns a transient error and rolls back the whole acceptance transaction.

Reclamation plans only exact issued objects from permanently closed producers, with no remaining root or backup custody reference. The first observed orphan receives at least 24 hours of grace; an old creation timestamp does not bypass that grace. A permanent candidate tombstone prevents later publication from resurrecting an object. Fenced claims renew real leases and recheck policy and references before every provider effect. Exact removed versions remain in the reconciliation ledger so a late version cannot be mistaken for an already completed cleanup.

The 2026-10-31 component checkpoint compiled this controller, passed its metadata pruning unit, and passed 15 native Source/writer/recovery regression tests. The dedicated expiration/provider fault integration fixture is a separate gate; these component results alone do not certify physical reclamation.

## Exact multipart reconciliation

Managed Dataset objects are durably issued under the real producer capability before InitiateMultipartUpload. An acknowledged provider upload ID is recorded through a protected helper that rechecks the actual native execution/task lease, namespace binding and incarnation. Raw ordinary-role inserts into producer, issued-object and upload-ID journals are denied. A permanent producer tombstone and a real fenced GC claim authorize bounded discovery at one exact issued object key; the provider page has at most 16 records. Only exact matching keys and upload IDs are exposed. Prefix siblings never acquire cleanup authority. Abort uses a distinct exact-ID capability. After deleting a page, reconciliation restarts from the exact key rather than relying on a deleted continuation marker. The durable watcher remains responsible for late Initiate effects.

The actual Dataset fault proof in `../evidence/2026-10-31/native-dataset-retention/multipart-v11-20261031T092054Z` covers a known Part acknowledgement, a lost Initiate acknowledgement, and a held Initiate that reaches the provider after the first collector pass. All three are cleaned while a neighboring upload survives. The late-effect branch waits a real 30-second watcher interval. Historical retention timestamps are explicitly synthetic closed DATA, and only exact never-claimed candidate IDs are pre-aged. Actual leases, claims and previously claimed watcher timestamps are unchanged.

## Restored Dataset qualification and target custody

A restore preserves original root/member/producer audit records. Under the actual disabled restore transaction, the private verified content-copy proof may add an immutable qualification for the new incarnation and target physical fingerprint. Qualified members derive only from the private copied inventory and actual target ObjectVersions, in pages of 64. Only complete qualified roots are sealed. Fresh destination objects are journaled under the actual restore identity without invented execution leases. Finite policies use the qualification matching the current incarnation and physical binding; an empty restored ownership ledger is never evidence for deleting old external custody.

The exact logical provider key `moria_restore_target_custody_v1` is permanently reserved in every restore target namespace. Its body binds the actual restore UUID, recovery set, inventory, namespace, physical fingerprint and target mapping. First acquisition checks absence of the exact copied inventory keys before creating the marker, then uses create-only object publication. An exact retry can recover existing matching objects only after verifying its own permanent marker. A different restore cannot adopt the marker. The marker's actual provider version and full body are checked before dispatch is enabled. It is outside Dataset issued-object journals, recovery content inventories and all Moria GC authority.

This establishes custody for the exact copied keys. It does not claim that a target prefix contains no unrelated objects. Operators must assign a separate physical namespace to different installations/restores and fence other writers; no global prefix-list authority is inferred. The marker admission path has local POSIX unit coverage for exact retries, later-restore rejection, identical unowned preexisting bytes and final marker tampering. The complete qualified S3 GC/backup/restore proof is recorded in `../evidence/2026-10-31/native-dataset-retention/20261031T101602Z-external.json` and its test log. It verifies source GC followed by old-backup recovery on a clean host, actual cell reassignment, exact historical/current typed rows, and rejection of a different restore reusing the later S3 target prefix while the original restored rows remain unchanged.

Native root/member and uniqueness certificates are written by the trusted kernel after private typed verification. The kernel database role is trusted; these records do not claim cryptographic resistance to compromised kernel database credentials. Protected lease helpers and ordinary-role DML guards enforce producer issuance and operator control boundaries. A caller-supplied certificate or authorized flag is never accepted from a connector, engine guest or HTTP request.

### Current metadata and explicit retained history

Current-table metadata compaction is independent of physical expiration. The controller may remove old snapshot records from the current Iceberg metadata while their exact immutable native roots and data remain retained. It preserves the current snapshot, real Iceberg references and imported snapshots that have no qualified historical Moria root. Snapshot-log entries are deduplicated within that retained set; metadata-log is bounded by publishing a fresh native root rather than recursively retaining every former metadata pointer. Physical expiration still requires the explicit policy, minimum age, actual pin checks and collection grace.

Historical Dataset selection happens at execution scheduling. `catalog::resolve_dataset_pin_at[_in]` checks current Dataset read/label/namespace authority and resolves the requested snapshot, optionally bounded by an as-of catalog revision, to an actual sealed, unexpired root with a current physical qualification. The resulting normal `DatasetPin` is installed in the execution's immutable inputs and receives the existing root pin. Accepted resource-only reads remain exact; a guest cannot enlarge its accepted input history later. An absent snapshot returns `DATASET_SNAPSHOT_NOT_FOUND`; a physically expired one returns `DATASET_SNAPSHOT_EXPIRED`.

The fresh proof in `../evidence/2026-10-31/native-retention/dataset-history-selection-v2-20261031T111934Z` uses young native roots without timestamp aging. It compacts two metadata snapshots to one with zero expired roots while a real old reader is active, accepts and reads a separately resolved old snapshot after compaction, rejects a future snapshot through an earlier as-of bound, and proves repeated compaction does not publish another head.
