# Native Source automations

Status: the trusted fixed-binding execution scheduler is implemented and tested. Source `Automation` factories described here are being implemented; Source activation must retain `DOMAIN_REGISTRATION_PENDING` until their native registration and worker proof pass.

An Automation selects `build`, `sync`, `invokeAgent`, or `evaluate`, an exact Source target, an Application, immutable input, and an interval. Timezone cron is outside the accepted declaration. A firing is keyed by Automation identity and its scheduled database UTC instant. Independent schedulers lock due rows with `SKIP LOCKED`; the unique firing key and its immutable input prevent duplicate scheduling. Missed intervals coalesce to one firing and an active linked child or in-progress dispatch produces an audited overlap skip.

Operator registration binds the Automation to a registered service authority, service target revision, resource class, bounded control timeout, and a separately registered target service revision. Configuration is metadata only. It cannot execute code, mint a session, call a provider, or require a Docker daemon on the API host. Current Automation/Application/target Source ACLs and markings, exact registered purpose, principal/application state, incarnation, and intersected operations remain authoritative at every dispatch.

The closed registration shape is `{serviceAuthority, serviceBindingRevision, targetServiceBindingRevision, resourceClass: "automation-control", controlTimeoutSeconds}` with a ten-to-six-hundred-second control deadline. Target Agent input is a bounded typed object. The current build, sync and evaluate factories require an empty Automation input object. Evaluation dispatch additionally requires the suite's separately registered Agent/evaluator service-purpose profile. Configuration alone does not establish worker readiness.

Each firing creates a bounded native control execution. An actual registered control-worker task lease is required before issuing its private job credential. The worker calls the existing domain factory so that each firing resolves the current accepted target release and current exact Dataset snapshots. It does not reuse an earlier execution binding. Arbitrary Function/Agent/Transform code retains its existing single-attempt rules.

The generic registered-service same-purpose guard remains strict. A private automation-only binding helper validates the live control/firing row, declared target, approved target service mapping, identical service actor/application, and accepted/current operation and marking intersections. It creates the target's own registered-service binding with an immutable firing-origin witness. This is dispatch lineage; the completed control is not a live user-code parent. Public JSON cannot select this path or provide an actor, credential, firing, service authority, or release. Source input classifications flow into the child and every Dataset output requires its explicit classification floor to admit them.

Child acceptance and the firing's child identity must commit in one domain acceptance transaction. After a lost response or control-process death, recovery reads that durable identity before parsing a newly deployed target release. It never dispatches a second child because the old response was lost or the target definition changed. The short-lived control renews only during dispatch and publishes a receipt after the child identity is durable; a long-running child holds no control task slot. Cancellation before that admission transaction commits fences dispatch. Later child cancellation and cleanup belong to the domain API/supervisor. Pausing a schedule affects subsequent firings; disabling a registered purpose is security revocation. Generations prevent an off/on pulse from reviving accepted work. Retained results revalidate the pinned Automation Source proof and classifications as well as the target's ordinary retained-evidence checks.

`GET /api/v1/automations/{id}/firings` exposes a structural audit page after current exact `{id}:run`, application scope, Source/dependency/file ACL and clearance checks. The inspector may differ from the internal scheduled service actor. Each row contains firing identity, scheduled UTC instant, scheduler outcome, the opaque control identity allocated before factory execution and constant `childView: "withheld"`, plus the union of its historical and current classifications. It contains no control terminal status, child identity/status/timing, input, output, logs, credentials, actor details or failure body. A factory can consume protected input before it creates a child, so even child presence or control success can become a data oracle. Those views require independent domain/operator inspection with full consumed-source authorization; clearance alone is insufficient.

Pages contain at most fifty records and 256 KiB. Ordering is descending scheduled instant then firing UUID. `nextAfter` is a JSON tuple of the returned RFC3339 UTC instant and UUID, passed unchanged as the URL-encoded `after` value; its maximum encoded value is 256 bytes. It is a position, never an authorization credential. Every continuation repeats current authorization and pinned historical Source proof. Malformed positions fail with `AUTOMATION_CURSOR_INVALID`. Private records never become public because later Source labels are removed.

Required real proof includes concurrent scheduling/coalescing/overlap audit, current target release and Dataset pin refresh, process death after accepted child commit before acknowledgement, disabled-and-reenabled registration revocation, cancellation, and deadline cleanup. These are separate from the existing fixed-binding scheduler proof and from production capacity certification.
