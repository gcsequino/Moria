# Moria security contracts v0.2

Markings, restricted views and object/property policies are accepted first-slice requirements. The reviewed defaults, including the terminal restricted-view boundary in S03, are accepted. It must be tested end to end, not inferred from an SDK type or database feature.

## S01 — identities, grants and policy composition

Authentication establishes principal, application, environment, session and delegation chain. User/group attributes used by policies are authoritative platform records synchronized from the identity provider, never client request fields. Platform-native membership/permission edits take effect at their security-epoch commit. Identity-provider-only changes take effect when synchronization commits; initial polling is at most 60 seconds while the provider is reachable, with stale identity synchronization failing closed after 60 seconds. This bounded external synchronization delay must be disclosed rather than called immediate revocation. Emergency platform session/principal disable is immediate at the next protected operation. Workload identity is distinct from a human. A delegated agent is constrained by its service permissions, application scopes and the initiating user's current permissions. Autonomous agents have no implied human privileges.

Authorization requires all of: current principal permission; currently granted application scope; active resource/environment restrictions; all required markings; relevant row/property predicates; and delegation constraints. Multiple ordinary grants may contribute permissions by union; restrictive policies compose by AND and explicit deny wins. No grant means deny. Owning a repository, resource or namespace is not permission to read all data or declassify it.

The CLI is a registered application with administrative scopes granted explicitly. `Grant` resources name principal/group subjects, application, target, operations and environment. An application declaration requests operations; requests cannot create grants. Namespace creation, ownership transfer, security writes and marking clearance use separately granted administrative operations. Source declarations cannot assign themselves a privileged principal.

## S02 — markings and propagation

A Marking declares an eligibility group and independent declassifier group. A caller must meet every marking on a resource, in addition to ordinary permission. Empty marking lists do not grant access. Effective markings include namespace/resource markings plus inherited input markings. Namespace marking additions apply immediately to existing resources and their derivation closure.

Transforms inherit the union of all input snapshot markings, including inputs whose values are filtered/aggregated away. Outputs, derived generations, action overlays and platform-controlled result artifacts retain applicable labels. Label removal requires explicit `declassify` authority for every removed marking, an audited reason and target revision; editing YAML or dropping a column does not declassify. Source mapping and transform code are not authorities to weaken labels.

Adding a marking to an already-used source must restrict descendants immediately. Initial implementation serializes marking changes with lineage publication, writes a current effective-label closure and bumps the security epoch atomically. If that cannot finish within transaction limits, put the affected project into fail-closed security maintenance while recomputing; do not advertise immediate propagation while asynchronously exposing old descendants. Removal is separately authorized, recomputes closure and cannot discard another inheritance path.

Follow-up research obtained substantive official documentation for [restricted views](https://www.palantir.com/docs/foundry/security/restricted-views), [their limitations](https://www.palantir.com/docs/foundry/platform-security-management/manage-restricted-views), and [access-control propagation](https://www.palantir.com/docs/foundry/security/access-control-propagation). The reference distinguishes per-user read filtering from mandatory propagation. Our specific engine/runtime contracts remain DESIGN, not claims of complete reference equivalence.

## S03 — restricted views

A RestrictedView references one backing Dataset and one row Policy. The policy is a bounded typed expression over row fields and current principal attributes. It is evaluated for each caller, not pre-materialized as one user's visible rows. Access to the view does not grant raw dataset access. Only platform indexing services may read the backing data under a narrow trusted binding; requesting users require view/object access, not the backing dataset grant.

An ObjectType maps either a Dataset or a RestrictedView as its canonical source. When using a view, indexing retains the necessary policy columns privately and serving enforces the view predicate. View security cannot be bypassed by querying the object type, links, aggregations, exports or retrieval. Restrictive row policies apply to both pinned and current source attributes as described in C05. Row-policy attributes are taken from canonical source data, not editable overlays, unless a later explicit policy migration changes that contract.

**D03 finalized:** RestrictedView is a terminal data-consumption resource, not a reusable transform input. All Transform inputs must resolve to Dataset resources; using a RestrictedView fails compilation before execution. Restricted views remain queryable and may back Ontology object types. Terminal does not mean frozen: the view continues to reflect its backing data and current policy. Transforms use backing datasets with an authorized service identity, and derived datasets inherit markings. This avoids accidentally persisting one caller's visible subset as generally accessible data. Read filtering does not attach a persistent row policy to bytes already exported; exports require explicit permission and platform-controlled output labels. Bulk view export is deferred; page reads remain available.

Authors may define a restricted view on a completed transform output. Any later transform must independently obtain access to a backing Dataset; view access never grants that access. Automatic policy preservation through transforms and direct RestrictedView transform inputs are out of scope. The [research note](storage-and-row-security.md) retains the alternatives considered, not pending requirements.

## S04 — object and property policy behavior

Object read policies filter objects before user predicates, counts, links and pagination are evaluated. A denied point read returns NOT_FOUND. Link traversal checks both endpoints and relation policy. Static and dynamic sets recheck all members; they cannot become permission snapshots.

Property read policies in v0.1 depend only on principal/group/application attributes, not row values. This makes authorization to filter/order/aggregate on a field independent of which hidden rows exist. Denied properties are omitted from returned JSON and listed only as schema-known redactions if requested; no value or null placeholder is returned. SDK result types distinguish optional restricted properties. Explicitly requesting a denied property or using it in a predicate returns `PROPERTY_FORBIDDEN`, regardless of whether matching rows exist. Omitted projection means all currently readable properties.

Object action eligibility, per-property write policy and action invocation scope are independent of read access. V0.1 requires read access to targeted existing objects; blind writes are deferred. Writes must satisfy before-state and after-state restrictions so an action cannot move data outside authorized bounds. A narrowly authorized security administration operation can change labels/ownership, but ordinary actions cannot. Creation checks the proposed row and required source-independent policies. Source-backed creation without policy attributes is invalid.

## S05 — policy expression language

Use a small JSON expression AST: literal, field, principalAttribute, parameter, eq/ne/lt/lte/gt/gte, in, isNull, contains, and/or/not. Resource schemas define the structural grammar; the compiler validates operand types and permitted contexts. Row policies can use field/principalAttribute; property policies can use principalAttribute; action conditions additionally use parameters and authorized fields. No dynamic SQL, arbitrary function calls, network access, clock access, regex or executable policy plugins in v0.1.

The evaluator uses three-valued null logic with allow only on true; missing principal attributes deny. Compile into parameterized SQL and a matching reference evaluator. Maximum AST depth 16, 256 nodes and 100 in-list values. Differential fixtures must show identical policy results for nulls, Unicode and arrays. The API database role must not own protected tables or have BYPASSRLS. RLS provides environment isolation as defense in depth; the platform compiler enforces the full policy contract. Policy content is data and must never be fed to a general JavaScript evaluator.

## S06 — revocation, caches and in-flight operations

Every authorization change increments an environment security epoch (or all affected environments). Membership and attribute changes increment it too. Each protected operation obtains a current policy snapshot from the authority, not just stale JWT claims. Cache keys include identity, application, delegation, environment, epoch, resource labels and query contract. No cross-user result cache initially. If the authority cannot be consulted, protected reads/writes fail closed.

The authorization point is explicit: for a bounded read it is immediately before releasing a response; recheck the epoch after query evaluation and retry/deny if it changed. A read that linearized before a revocation can finish delivery; revocation cannot retract bytes. An action locks/checks the security epoch within its commit transaction so a racing security update orders before or after it. Future pages with changed epochs fail; they do not reuse old authorization. Long-running workers reauthorize at data reads, output commits, tool calls and external dispatch. Cancellation on revocation is best effort; output blocking is authoritative.

For AI streams and event streams, check current authority at each emitted batch and before new model/tool dispatch; stop after a failed check. Data already sent to a provider is outside recall. Logs/results/checkpoints are protected artifacts and cannot be retrieved through a generic activity-list bypass. Activity discovery filters entries by current access and emits only safe summaries.

## S07 — model destinations, retrieval and arbitrary code

Every ModelProvider declares a destination classification. A model-destination Policy declares allowed destination names and markings; for marked content all its markings must be allowed. Absence of a destination policy denies dispatch. Gateway checks effective identity plus marking eligibility and destination permission before inference or embedding. A model provider secret never enters agent/frontend code.

The runtime records the union of labels for data read during an execution and attaches it to generated artifacts, prompts, traces, results and tool outputs. Conservative execution-level labeling is the default: an agent cannot drop a label by constructing a new string. Delegated execution checkpoints also retain user/application identity and source references; a resumed execution reauthorizes its inputs. Unlabeled external user input is not proof of public provenance; configuration establishes its classification.

User workers have no direct provider network path or raw blob-store/control-database access. Egress is denied by default. Connectors receive explicit source/destination access; other network access must be declared and enforced through the supervised runtime/proxy. Arbitrary network grants can exfiltrate readable data, so they require administration authority and destination checks; merely requiring OSDK use is insufficient. A single trusted organization is not a claim of mutually untrusted tenant security or complete information-flow tracking after bytes leave platform-controlled paths.

Retrieval chunks retain source identity, source revision, object/property provenance and labels. Embedding requests obey the same destination checks as inference. Search applies current permissions to candidates before passages, scores, provenance or counts become visible. Exact search over authorized candidates is the initial implementation. Deleted/currently inaccessible source content is excluded even if its embedding remains. Security changes invalidate caches; content deletion removes chunks during cleanup. A collection indexed from restricted views must retain per-document security context, not a builder's visible subset. Document ingestion uses text fixtures initially, with no bundled production connector.

## S08 — secrets, audit and verification

SecretReference declarations contain logical names and allowed consumer resource references, never values. Values are encrypted at rest with an operator-held root key outside the database backup; worker credentials are short-lived and per execution. Logs redact known secret values and headers, but code may intentionally transform them, so access grants and output isolation remain necessary. Default traces contain structural events/IDs/timings; prompt/output bodies require explicit opt-in and inherit labels.

Audit is committed with changes and records principal, application, delegation, operation, target IDs, revisions, time, outcome and correlation ID. Denied attempts are logged without forbidden values. Audit is protected from ordinary application mutation; database administrators remain a trusted operational boundary. First-slice acceptance includes restricted counts/link traversal, denied property predicates, source marking propagation, delegated revocation, filtered retrieval and forbidden model destinations.
